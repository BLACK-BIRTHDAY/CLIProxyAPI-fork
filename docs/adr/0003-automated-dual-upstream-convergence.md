# Automated Upstream Convergence with Agentic Conflict Resolution and Gated Container Publishing

Status: accepted

Because this repository maintains custom Cloud Run hardening (Antigravity anti-ban protection, GCS FUSE bbolt fallback, trusted proxy auto-detection, and native C ABI plugin support) on top of upstream `router-for-me/CLIProxyAPI`, routine upstream advances frequently collide in shared server bootstrap and management files.

We decided to:
1. **Run an Automated Upstream Sync Cycle**: Schedule a daily (`0 0 * * *` UTC) and `workflow_dispatch`-triggerable GitHub Actions pipeline (`.github/workflows/upstream-sync.yml`) that fetches and merges `router-for-me/CLIProxyAPI` `main` with `--no-commit --no-ff`.
2. **Enforce Zero-Dependency Agentic Conflict Resolution Behind Verification Gates**: When `git merge` produces conflicts or `go build ./cmd/server` / `go test ./...` fails after merging, invoke a self-contained Node.js OpenAI-compatible tool-calling agent (`scripts/ci-upstream-agent.mjs`) backed by `UPSTREAM_AGENT_BASE_URL` / `UPSTREAM_AGENT_API_KEY` / `UPSTREAM_AGENT_MODEL` (`gemini-3.8-flash-high`). The agent is strictly bounded by `gofmt`, `go build ./cmd/server`, and `go test ./...` verification gates; if verification remains red after exhausting its turn budget, the workflow aborts promotion to `main`, pushes the state to a Quarantine Sync Branch (`upstream-sync/failed-<sha>`), and opens or updates a diagnostic GitHub Issue.
3. **Chain Container and Windows Update Package Publishing In-Process Without PAT Loops**: Because pushes authenticated with the default `GITHUB_TOKEN` do not trigger separate `on: push` workflows, `.github/workflows/docker-publish.yml` exposes `on: workflow_call` (alongside `push` and `workflow_dispatch`) and builds both the Linux container image (`ghcr.io/black-birthday/cliproxyapi:latest` and `:<short_sha>`) and the Windows x64 update bundle (`CLIProxyAPI_windows_amd64.zip` and `cli-proxy-api-windows-amd64.exe`, including `static/management.html` and `config.example.yaml`, published to the rolling `latest` GitHub Release and Actions Artifacts) in the same workflow execution whenever verified upstream advances are promoted.
