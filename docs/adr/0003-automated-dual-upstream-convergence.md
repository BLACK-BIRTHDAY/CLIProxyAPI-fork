# Automated Dual-Upstream Convergence with Agentic Conflict Resolution and Gated Container Publishing

Status: accepted

Because this repository is a downstream convergence of `router-for-me/CLIProxyAPI` (integrated via source-level Git history across server bootstrap, management v8 handlers, and model registries) and `BUKOWSKIREAL/magpie-gemini-web` (integrated via the Studio Release Pin in `Dockerfile` and `internal/magpie/process.go` plus Go-ported adapter logic in `internal/magpie/`), routine upstream advances frequently collide in shared hook files or introduce new MAGPIE backend capabilities.

We decided to:
1. **Run a Single-Workflow Dual-Upstream Sync Cycle**: Schedule a daily (`0 0 * * *` UTC) and `workflow_dispatch`-triggerable GitHub Actions pipeline (`.github/workflows/upstream-sync.yml`) that (a) fetches and merges `router-for-me/CLIProxyAPI` `main` and (b) inspects `BUKOWSKIREAL/magpie-gemini-web` releases for newer `studio-v*` (`build.json`) and `v*` plugin tags to advance the Studio Release Pin (`Dockerfile` URLs/SHA-256 digests and `MagpieStudioVersion`).
2. **Enforce Zero-Dependency Agentic Conflict Resolution Behind Verification Gates**: When `git merge` produces conflicts, `magpie-gemini-web` introduces Go-adapter deltas, or `go build ./cmd/server` / `go test ./...` fails after merging, invoke a self-contained Node.js OpenAI-compatible tool-calling agent (`scripts/ci-upstream-agent.mjs`) backed by `UPSTREAM_AGENT_BASE_URL` / `UPSTREAM_AGENT_API_KEY` / `UPSTREAM_AGENT_MODEL` (`gemini-3.8-flash-high`). The agent is strictly bounded by `gofmt`, `go build ./cmd/server`, and `go test ./...` verification gates; if verification remains red after exhausting its turn budget, the workflow aborts promotion to `main`, pushes the state to a Quarantine Sync Branch (`upstream-sync/failed-<sha>`), and opens or updates a diagnostic GitHub Issue.
3. **Chain Container Publishing In-Process Without PAT Loops**: Because pushes authenticated with the default `GITHUB_TOKEN` do not trigger separate `on: push` workflows, `.github/workflows/docker-publish.yml` exposes `on: workflow_call` (or runs as a downstream job in the same workflow execution) so verified upstream advances pushed to `main` (and fast-forwarded to `feat/magpie-cloud-run`) immediately build and publish refreshed `ghcr.io/black-birthday/cliproxyapi:latest` and `:<short_sha>` images in the same run.
